Overview

All device APIs are prefixed with /api/ and are mounted under the main Django project. Version/firmware APIs are under /versions/api/.

Device APIs Prefix: /api/
POST /api/authenticate/ Authenticate a device and obtain an encrypted ID

Validates device credentials and returns a base64-encoded device identifier used in subsequent API calls.

Request Parameters
FieldTypeRequiredDescription
devise_idstringrequiredDevice hardware ID
keystringrequiredDevice secret key
Response — Success (200)
{"message": "Authenticated", "device_id": "<base64-encoded-id>"}
Response — Failure (400 / 404)
{"message": "Invalid credentials"}

Firmware / Version APIs Prefix: /versions/api/ — No authentication required
GET /versions/api/check-active-version/ Check if an update is available

Compares the device's current version against the active version in the system.

Query Parameters
ParamTypeRequiredDescription
versionstringrequiredCurrent firmware version, e.g. v1.0.0
Example
GET /versions/api/check-active-version/?version=v1.0.0
Response — Up to date (update=0)
{"version": "v1.0.0", "update": 0, "message": "You have the latest version"}
Response — Update available (update=1)
{"version": "v1.0.0", "update": 1, "message": "Update available: v1.2.0"}
Response — No active version
{"version": "v1.0.0", "update": 1, "message": "No active version available, please update"}
When update=1 the device should call the download endpoint to fetch the new firmware file.
GET /versions/api/download-version/ Download the active firmware file

Streams the currently active firmware/app file directly. No parameters required.

Example
GET /versions/api/download-version/
Response — Success

Binary file stream with headers:

Content-Type: application/zip  (or application/vnd.android.package-archive for .apk, etc.)
Content-Disposition: attachment; filename="v1.2.0.zip"
Response — No active version (200 JSON)
{"version": null, "active": 0, "message": "No active version available"}
Supported file types

.tar.gzapplication/gzip
Authentication Flow

Device APIs use a two-step authentication model:

  1. Device calls POST /api/authenticate/ with its devise_id and key.
  2. On success, receives a base64-encoded device_id.
  3. All subsequent data submission calls include this device_id in the request body.
The encoded device ID is validated on every data call — invalid or tampered IDs return HTTP 400.
